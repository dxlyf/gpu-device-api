这一版量的是**真实负载**：几何体是盒子（24 顶点 / 36 索引 / 12 三角形，position + normal + uv 三个属性）， 片元着色器做方向光 + 半球环境光 + 基于 uv 的明暗，所以顶点数、属性带宽、矩阵运算、填充率都不是零成本。 默认（?motion=on）下**每个物体每帧都在动**：各自的自转角速度、相位、环绕半径、上下浮动幅度 （确定性哈希生成，刷新后画面一致）每帧重算 model = T·R·S 并**把整段每物体矩阵重新上传** —— 旧版把这一整块成本藏起来了。选「静态」或加 ?motion=off 可只测「矩阵上传一次」， 动态档里也会自动跑一遍静态对照，直接给出「动起来多花多少」。

计时口径：每档先热身几帧，然后测两轮。第一轮完全不同步 —— 只计时 「重算矩阵 + 上传 + 录制 + 提交」的 CPU 时间（队列空着起跑，因此最接近纯 CPU 成本； 驱动队列满时会被反压）。第二轮逐帧同步 —— WebGL2 用 1×1 readPixels 强制同步（gl.finish() 在 WebGL 里并不保证 GPU 做完），WebGPU 用 queue.onSubmittedWorkDone()。同步这一轮把 CPU/GPU 串行化，所以 「帧耗时(均值,含同步)」是**偏悲观的上界**，「GPU 同步等待」是提交后等后端做完的时间。 大档会按 framesForCount 降帧（见「测帧数」），单帧探测超过 2 秒的档会跳过。 注意在软件光栅化（SwiftShader）上，GPU 一帧要几十毫秒，不同步那一轮很快就被驱动队列反压， 所以它的均值会偏高、帧间方差也大 —— data-benchmark-cpu-submit 里的 min 才是最干净的「纯 CPU 一帧」。每 draw µs 在实例化模式下分母是 1 次 draw call（等于整帧 CPU 时间），看每物体 µs才有意义。 另外在 GPU 受限时（尤其是软件光栅化），「移动开销 Δ帧」可能接近 0 甚至为负：这一帧的 CPU 矩阵重算与上一帧的 GPU 工作重叠了，只有 ΔCPU 如实反映「动起来」的代价。

渲染通道的深度附件来自 context.createPassDescriptor()：canvas 纹理本身没有深度附件， 旧版直接用帧 view 拼 colorAttachments，结果是 WebGL2 静默关掉 DEPTH_TEST、 WebGPU 解析成没有深度状态的管线变体。跑完还会做一次离屏 readback 自检： benchmarkLit 证明真的画出了东西，benchmarkMoved/benchmarkMotionPixels 证明动态模式下相隔 0.5 秒的两帧画面确实不同。查询参数： ?backend=webgl2|webgpu|auto&mode=instanced|draws&motion=on|off&frames=30&counts=2000,5000。
