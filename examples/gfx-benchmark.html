CPU 提交是 beginFrame → 逐 draw → endFrame 里 CPU 花的时间； GPU 执行来自后端的 query 机制（WebGPU：timestamp-query + encoder.writeTimestamp；WebGL2：EXT_disjoint_timer_query_webgl2）， 是环形 query set + 延迟若干帧的异步读回，不会每帧阻塞等 GPU。 两列不是同一个量：调用 renderer.enableGpuTiming() 之前 GPU 那列是 —（不是 0）。 拿不到 GPU 计时的原因（缺 feature / 缺扩展 / disjoint）写在 data-bench-gpu-error 里。

配对 A/B（推荐用这个看收益）：ab=split 或 ab=cull 会在**同一个页面里 交替**测两种配置（split=1/0 用两条材质切换，culling=1/0 用渲染器的开关切换）， 每档跑 rounds 轮（默认 3）、每轮取最小帧耗时再比 —— 机器上有别的负载时， 跨次运行的数字能在 9ms 与 278ms 之间摆动，只有这种交替测量才说明得了问题。 结果写在 data-bench-ab：档:off=..ms,on=..ms,deltaPct=..,drawCalls=..,culled=..。 剔剔除的对照建议配 spread=60（物体铺得开，才真的有东西被剔掉： spread=10 在这种超宽画布下几乎全部可见，剔除数是 0）。

这一页和 core 层基准 测的是**同一件事的两个层次**：core 基准手写 着色器/缓冲/bind group/管线/通道，所以它看不到便捷层的开销；本页只用 src/gfx， 每个物体一次 renderer.draw()，每次 draw 都要走：相机 uniform、自己的 model、自动计算的法线矩阵（lambert 声明了 normalMatrix）、 uniform arena + 动态偏移、bind group，以及按材质属性逐个绑定顶点缓冲（3 个属性 = 3 次 setVertexBuffer）。两页同档的「CPU 提交(均值)」可以直接相减，差值就是便捷层的净开销。

同一份构建下的三个开关（刷新页面时带上参数即可，用来做 A/B）： split=1|0 关掉 scene / per-draw 的 uniform 拆分（split=0 时材质写成 sceneFields: false，所有字段回到一个块、每 draw 整块重写 —— 也就是拆分前的行为）； culling=1|0 打开视锥剔除（打开后 draw calls 会小于物体数，差额是 「剔除/跳过测试」列的前一个数字，也写在 data-bench-culled 里）； sort=none|opaque|all 打开 draw 排序（按管线 → 绑定组 → 深度；半透明物只按深度 从远到近，绝不被管线分组打乱）。三个开关都可以用 data-bench-split / data-bench-culling / data-bench-sort 抓取。

计时只算 CPU 时间（frames 是每档测量的帧数，先空跑几帧热身）。帧与帧之间只 await device.queue.onSubmittedWorkDone()，**故意不做** core 基准那个 1×1 readPixels 强制同步 —— 那个技巧是为了把 GPU 时间算进帧耗时，代价是每帧把 GPU 串行化。 交叉验证 GPU 那列是否可信：它应当与「含等待后端 − CPU 提交」同量级（后者是另一条包含 GPU 执行时间的路径）。
